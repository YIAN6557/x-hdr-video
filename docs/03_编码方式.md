# 编码方式

先记住：下面的方法只在"X 会读色彩信息"的账号上有效。正式发之前，用一条几秒的测试帖和 `tools/check_x_video.sh` 确认自己的号能保留 HLG（见 [README](../README.md#先测你的账号)）。

## 规格

| | 发 X | 自己在 iPhone 上看 |
|---|---|---|
| 编码 | H.264 High | HEVC Main 10，标签 `hvc1` |
| 位深 / 采样 | 8 位，yuv420p | 10 位，yuv420p10le |
| 色彩 | HLG（arib-std-b67）+ BT.2020，矩阵 bt2020nc，limited range | 同左 |
| 标签写在哪 | **码流（VUI）和容器都写** | 码流和容器都写 |
| 杜比视界 | 不要 | 不要 |
| 文件 | `.mp4`（`+faststart`） | `.mov` |
| 上传 / 传输 | 电脑浏览器打开 x.com，直接传，不裁剪不编辑 | 隔空投送到相册 |

两个版本的区别：

- H.264 8 位 HLG 存成 `.mp4` 隔空投送到 iPhone 相册，不按 HDR 播放；存成 `.mov` 就按 HDR 播放（11-01 测）。要从 iPhone 的 X app 发，就用 H.264 8 位 HLG 的 `.mov`（把下面命令的输出名改成 `.mov` 就行）。
- HEVC 发到 X，会被转成普通视频。

8 位不会出色带吗？我们比过同一帧：不压缩时，8 位和 10 位几乎一样（SSIM 0.999）；画面里有颗粒或细节时，颗粒本身就起抖动的作用，把黄昏暗处的对比拉高 3 倍也看不到色带。纯色大渐变（比如干净的天空）要自己抽帧检查。

## 方法 A：已经有 HLG 母版

比如达芬奇、Final Cut 导出的 HEVC 10 位 HLG，转成发 X 的格式：

```bash
ffmpeg -i 母版_HLG.mov -c:v libx264 -preset slow -crf 18 -profile:v high -pix_fmt yuv420p \
  -x264-params "colorprim=bt2020:transfer=arib-std-b67:colormatrix=bt2020nc" \
  -color_primaries bt2020 -color_trc arib-std-b67 -colorspace bt2020nc -color_range tv \
  -c:a aac -b:a 192k -movflags +faststart 发X用.mp4
```

- 这条命令只降位深、换编码，不改颜色。我们用一支 HEVC 10 位 HLG 测过：前后同一帧的平均 Y / U / V 只差约 0.2%，码流里的 VUI 是 9 / 18 / 9。
- `-x264-params` 那一行把标签写进码流；`-color_primaries` 那一行写进容器。**两行都要。**
- 常见错误：在别的软件里导出后，用 `ffmpeg -c copy` 加标签。这样只改了容器，码流里还是旧的，X 可能会忽略。
- 码率：CRF 16–18 就够了。X 收到后会再压到约 10 Mbps，给太高没有意义。

## 方法 A2：已经有 PQ / HDR10 母版

先看母版是哪一种：

```bash
ffprobe -v error -select_streams v:0 -show_entries stream=color_transfer -of csv=p=0 母版.mov
```

- `arib-std-b67` = HLG，用方法 A。iPhone 拍的 HDR 视频也是 HLG（另外带杜比视界），用方法 A 重新编码时，杜比视界会自动去掉。
- `smpte2084` = PQ（HDR10，达芬奇、LumaFusion 常见的 HDR 导出），要先转成 HLG。直接发 PQ，X 会把它转成普通视频（@naundob 第 1 次就是这样）。

```bash
ffmpeg -i 母版_PQ.mov \
  -vf "zscale=t=arib-std-b67:p=bt2020:m=bt2020nc:r=tv:npl=1000:d=error_diffusion,format=yuv420p" \
  -c:v libx264 -preset slow -crf 18 -profile:v high \
  -x264-params "colorprim=bt2020:transfer=arib-std-b67:colormatrix=bt2020nc" \
  -color_primaries bt2020 -color_trc arib-std-b67 -colorspace bt2020nc -color_range tv \
  -c:a aac -b:a 192k -movflags +faststart 发X用.mp4
```

- 需要带 zscale（libzimg）的 ffmpeg：`ffmpeg -filters | grep zscale` 有输出就行。
- `npl=1000`：按 1000 尼特的屏幕把 PQ 换算成 HLG（ITU-R BT.2408 的做法）。我们测过：PQ 的标准白（203 尼特）转完是 HLG 75%，正好是标准白该在的位置。高于 1000 尼特的部分会被削平；大多数 HDR10 本来就是按 1000 尼特做的。
- `d=error_diffusion`：从 10 位降到 8 位这一步由 zscale 来做，同时加抖动，防色带。
- 网上流传的版本在这里用 `format=yuv420p10le,noise=c0s=2:c0f=t,format=yuv420p` 防色带。我们测过，它不起作用：ffmpeg 的 noise 滤镜不支持 10 位，会先自动转成 8 位、再加噪点（加 `-v verbose` 能看到自动插入的 `auto_scale`），结果只是多了一层颗粒。
- 验证：把方法 A 用的 HLG 母版转成 PQ，再用这条命令转回 HLG，同一帧的平均亮度（8 位 Y）从 164.59 变成 164.73，差不到 0.1%；码流里的 VUI 是 9 / 18 / 9。

## 方法 B：只有普通（SDR）成片

用 `tools/hdr.sh`，一条命令做完"生成 LUT → 套 LUT → 编码 → 打印检查结果"：

```bash
zsh tools/hdr.sh <普通版视频> <倍数> <输出.mp4 或 .mov> [配乐文件]
```

- **输出扩展名决定格式**：`.mp4` = 发 X（H.264 8 位），`.mov` = iPhone 本机看（HEVC 10 位，需要 macOS 的 avconvert）。
- **倍数**：普通版里的白色在手机上是界面白的几倍。常用 2、3、4、5，**5 是上限**（白色落在 HLG 峰值）。也可以直接写尼特数：441 ≈ 2 倍，662 ≈ 3 倍，882 ≈ 4 倍，1104 ≈ 5 倍。
- **实拍素材只推高光**：`EXPAND="0.772 4.6" zsh tools/hdr.sh 素材.mp4 203 输出.mp4`。白色和界面白一样亮，只有本来就很亮的地方（信号高于 0.772）渐进提亮，到纯白时 4.6 倍；会先在 16 位里 deband，防天空出色带。

内部做法：

1. `make_lut.py` 生成 65³ 的 3D LUT：BT.709 → 线性光 → 按倍数放大 → BT.2020 → HLG。颜色超出峰值时等比例压回去，色相不变。
2. ffmpeg 先把画面转成 16 位 RGB 再套 LUT（`lut3d`，四面体插值），避免在 8 位里做运算出色带。
3. 编码：`.mp4` 用 x264 CRF 16、High@4.2、码率封顶 50 Mbps；`.mov` 用 x265 CRF 14、关 SAO，再用 `avconvert --preset PresetPassthrough` 只换苹果封装。**不要用 `PresetHEVCHighestQuality`**，它会重新压缩，画面变糊。
4. 打印 ffprobe 标记、有没有杜比视界、开头 / 中间 / 结尾三帧在苹果解码下的亮度。

## 亮度怎么定

- **先看内容**：不开 HDR、在普通屏幕上，这个画面也会让人停下来吗？HDR 只是放大器。
- **亮要落在天然该亮的东西上**：阳光下的云、雪、海面反光、灯、太阳。
- **亮的面积要够大**：@banbudev 的经验是，只有几个小亮点，在手机上看起来和普通视频差不多；大片天空、海面推进高光区才明显。
- **插画、动画用整体提亮**：整个画面按同一个倍数提亮，颜色关系不变。不要只提亮白色，局部发光像故障。
- **实拍用只推高光**：天空、反光本来就比别的亮，只推它们是自然的。
- 参考：骑车参考片大约一成的画面比界面白亮；我们的动画 5 倍时，白天画面约一半比界面白亮。
- 白天在户外，手机屏幕只比界面白多亮约 2 倍，再亮也看不出区别；室内、暗处，3 / 4 / 5 倍的差别才明显。
- 有人觉得太亮刺眼。发的时候可以在文案第一行加一句提醒，比如"晚上看请调低亮度"。

## 检查

```bash
# 1. 标记：要看到 h264 / High / yuv420p / arib-std-b67 / bt2020
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,pix_fmt,color_transfer,color_primaries -of csv=p=0 发X用.mp4

# 2. 码流里的标签（VUI）：要看到 9、18、9
ffmpeg -hide_banner -i 发X用.mp4 -c:v copy -bsf:v trace_headers -frames:v 1 -f null - 2>&1 \
  | grep -E "colour_primaries|transfer_characteristics|matrix_coefficients"

# 3. 没有杜比视界：这条命令不应该有输出
ffprobe -v error -show_streams 发X用.mp4 | grep -i dovi

# 4.（macOS）苹果系统认不认它是 HDR、实际多亮
swift tools/check_hdr.swift 发X用.mp4
swift tools/edr_probe.swift 发X用.mp4 3.0      # 3.0 = 第几秒；1.0 = 界面白
```

统计亮度时，要直接读原始 Y 平面（`tools/luma_stats.py`）。不要先用 `format=gray` 转换再统计，它会把范围拉伸，给出假数据。

发出去以后：

```bash
zsh tools/check_x_video.sh https://x.com/你的账号/status/帖子ID
```

## 可以直接发给 AI 的提示词

> 帮我把 [视频路径] 做成 HDR 版本，目标是发到 X 上，在 iPhone 的 X app 里比周围界面明显更亮。
>
> 要求：
> 1. 发 X 用的格式：H.264（High）8 位 yuv420p，.mp4；HLG 曲线 + BT.2020 色域；不要杜比视界。HLG 和 BT.2020 的标签要同时写进编码参数（x264 的 colorprim / transfer / colormatrix）和文件容器。
> 2. 再出一个自己在 iPhone 上看的版本：HEVC 10 位，标签 hvc1，.mov。（H.264 8 位存进 iPhone 相册不会按 HDR 显示，两个版本不能混用。）
> 3. 正确转换：原片是普通 SDR（BT.709），要在 16 位 RGB 里用 3D LUT 做真正的色彩转换，不能只改标签。如果原片已经是 HDR：HLG 只重新编码；PQ（HDR10）先用 zscale 按 1000 尼特转成 HLG，降到 8 位时加抖动。
> 4. 亮度：
>    - 实拍：原片的白色对应 HLG 75%（标准白），只把天空、云、阳光、灯光这些本来就亮的地方推到 HLG 90%–100%，高于 75% 的像素控制在 5%–10%。
>    - 插画、动画：整个画面按同一个倍数提亮，颜色关系不变；最亮把原片的白推到 HLG 100%（约手机界面白的 5 倍）。不要只提亮白色，局部发光像故障。
> 5. 画质：H.264 用 x264 crf 16–18，码率 15–50 Mbps 都可以（X 收到后会再压到约 10 Mbps）；HEVC 用 crf 14、关掉 SAO；不要用 avconvert 的 HighestQuality 预设，它会重新压缩、画面变糊。
> 6. 检查：
>    - 用 ffprobe 确认 h264 / High / yuv420p / arib-std-b67 / bt2020，并且没有杜比视界；
>    - 用 trace_headers 确认码流里的 VUI 是 9 / 18 / 9；
>    - 直接读原始 Y 平面统计亮度，不要先转成 gray，那样会把范围拉伸；
>    - 抽几帧把暗部对比拉高，看 8 位有没有一条一条的色带；
>    - 做一张亮度分布图给我看：黄色 = 高于 75%，橙色 = 高于 90%；
>    - 亮的面积要够大：只有几个小亮点，在手机上看起来会和普通视频差不多。
> 7. 另外导出一版原始 SDR，方便我对比。
>
> 发帖：用电脑浏览器打开 x.com，直接上传 .mp4，不要裁剪、不要编辑。不要从 iPhone 相册用 X app 发。发完下载 X 播放的文件，用 ffprobe 看 color_transfer 是不是还是 arib-std-b67；如果没有标记了，说明这个账号 X 还没开放 HDR，换格式也没用，马上删帖、改发普通版。
